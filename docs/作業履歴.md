## 2026-08-18 「たべた！」ボタン常時表示・リングサイズ調整・ロケット演出

対象ファイル: `index.html`（単一ファイル構成）

### 1. 「たべた！」ボタンをすぐ押せるように

これまで手動判定ボタンは設定パネル（設定ボタン → パネルを開く）の中にしかなく、
反応しなかったときに2タップ必要だった。

- 画面右下に常時表示の丸ボタン `#biteBtn`（104×104px）を追加
- カメラ開始と同時に表示、タップで `manualBite()` を実行
- タップ時に黄色い波紋（`.tapped`）でフィードバック
- `touch-action:manipulation` でダブルタップズームを抑止
- 設定パネル内の「いま たべた！」も従来どおり残置（同じ処理を共有）

### 2. リングのサイズを調整可能に

リングの大きさは CSS の `34vmin` 固定、検知範囲の `ringR=.17` も別々のハードコードだった。
CSS 変数 `--ring-size` に一本化し、JS の `applyRingSize()` から両方を同期させる。

- CSS 変数 `--ring-size` を追加、`#ring` の幅・高さ・マージンを `calc()` で連動
- `ringR = ringVmin / 200` で検知 ROI の半径をリング表示と一致させる
- 変更手段は4通り
  - 設定パネルのスライダー「わっかの おおきさ」（14〜60vmin）
  - リング上での2本指ピンチ（`pointerdown/move` を `Map` で多点管理）
  - マウスホイール（PC用）
  - キーボード `+` / `-`（リングにフォーカス時）
- サイズ変更時は `prevGray=null; warm=0` で明るさ学習をやり直す（ROIが変わるため）
- 設定・リング位置を `localStorage`（キー `mogumogu-camera:v1`）に保存し次回復元

### 3. ロケット演出の追加

ひとくちごとに燃料が溜まり、完食で発射する演出を追加。

**燃料が溜まる段階**
- 画面左下に6段の燃料ゲージ `#gauge` とロケット `#ship` を配置
- ひとくちごとにセグメントが点灯、炎 `#flame` が 5px ずつ伸びて揺らめく
- 音: 既存のチャイムに加え、燃料が溜まる上昇音 `charge()`（sawtooth のスイープ）
- 小さな噴射パーティクルがロケット下から吹く
- 残り1マスになるとロケットが小さく上下に跳ねる（`.ready`）

**発射シーケンス**（`completeSequence()`、`later()` で全タイマーを管理）

|---|---|
| 0.6s | 「おべんとう かんせい！」＋ファンファーレ＋音声 |
| 1.7 / 2.35 / 3.0s | カウントダウン 3・2・1（大きな数字＋電子音） |
| 3.65s | 「はっしゃ！」フラッシュ・画面シェイク・ロケット上昇・轟音・噴射／煙パーティクル・星の連続バースト |

## 2026-08-18 動き検知のオフ・大ロケット演出・完了口数の可変

対象ファイル: `index.html`

### 1. 動きの検知をオフにできるように

「勝手に反応しすぎる」ことがあるため、検知そのものを止められるようにした。

- 設定パネルに「うごきを みる」トグル `#detect` を追加（既定はオン）
- オフのあいだは描画ループの中で `detect()` を呼ばない（判定処理ごとスキップ）
- オフのときはリングを薄く（不透明度 .28）点線表示にし、
  ラベルを「てどうモード：みぎしたの「たべた！」で すすみます」に差し替える
- オフでも「たべた！」ボタンと設定パネルのボタンは従来どおり動く
- オンに戻したときは `prevGray` / `warm` / `baseline` を初期化して明るさ学習をやり直す
- 状態は `localStorage` に保存

### 2. ロケットの発射演出を大型化

小さなロケットが端で飛ぶだけだったのを、画面中央に大きく登場してから飛ぶ構成に変えた。

- 大ロケット `#bigRocket` を追加。絵文字サイズは `clamp(96px,36vmin,260px)`
  （従来のはっしゃ台のロケットは 42px なので、画面の短辺に対しておよそ3〜6倍）
- 中央寄せ用の `transform` と演出用の `transform` が衝突しないよう、
  外側 `#bigRocket` で中央寄せ、内側 `#bigStack` にアニメーションを当てる二重構造にした
- 衝撃波 `#shock`（中央から6.5倍に広がる輪）と、強いシェイク `#stage.shake.hard` を追加

**発射シーケンス**（`completeSequence()`）

| 時刻 | 内容 |
|---|---|
| 0.6s | 「おべんとう かんせい！」＋ファンファーレ＋音声 |
| 1.4s | はっしゃ台のロケットが消え、大ロケットが画面下から中央へせり上がる（風きり音 `whoosh()`） |
| 2.1s | エンジン始動。ぶるぶる震え（`.rev`）＋画面シェイク開始 |
| 2.2 / 2.8 / 3.4s | カウントダウン 3・2・1。数えるごとに炎が 40→62→84px に伸び、噴射も増える |
| 4.0s | **ドカーン**。フラッシュ・衝撃波・強シェイク・轟音、炎110pxで画面外へ。噴射の火花を35msごとに16個、煙44個、星のバースト12連発 |
| 5.9s | シェイク終了 |
| 6.4s | 「また あしたも たべようね」＋盤面リセット |

その他: 噴射パーティクルの上限を900→1200個に、轟音の音量とスイープ幅も拡大。

### 3. 完了までの口数を可変に

6口固定だったものを **2〜12口** で変更できるようにした。

- 設定パネルにスライダー `#goal`（現在値を数字で表示）
- `buildBoard()` で弁当箱のマスと燃料ゲージを口数ぶん組み直す。
  おかずの絵文字は6種なので `OKAZU[i % 6]` で循環させる
- 7口以上は2段組にする（列数 = `Math.ceil(goal/2)`）
- **1マスが巨大化する問題の修正**: `1fr` 列と `aspect-ratio:1/1` の組み合わせでは、
  列が少ないと1マスが219pxまで肥大した（口数2で弁当箱の高さが237px）。
  列数から弁当箱の横はばを決める（`min(92vw, 列数×76px)`）ようにして、
  どの口数でも1マス63〜68pxに収まるようにした
- 弁当箱の高さが口数で変わるため、CSS変数 `--deck` を実測値から更新するようにした。
  「たべた！」ボタン・ロケット・設定パネルの縦位置がこれに追従する
- 炎の伸び幅も口数に応じて調整（`38/goal` px ずつ）してはみ出さないようにした
- ドラッグ中は数字だけ動かし、指を離した時点（`change`）で組み直す
- 途中で口数を減らして到達済みになった場合は、そのままお祝いへ進む

### 動作確認

`requestAnimationFrame` を `setTimeout` に差し替え、口が開閉する擬似カメラ映像を
`getUserMedia` に注入して、検知から発射までを通しで確認した。

- 描画ループ: パーティクルがCanvasに1953px描画されることを確認
- 検知: ROI内の平均差分16.32（しきい値9）で `bites` が加算されることを確認
- 検知オフ: 3.5秒間はげしく口を開閉しても `bites` が0のまま。
  リングに `.off` が付き不透明度0.28、ラベルも切り替わる。ボタンは有効
- 口数: 2 / 3 / 6 / 9 / 12 でマス数・ゲージ段数・列数・`--deck` が追従、
  1マス63〜68pxに収まることを確認
- 口数を下げて到達済みになったケースでお祝いが始まることを確認
- 発射シーケンス: 登場（1.6s）→ 震え＋カウントダウン（2.2〜3.6s、炎40→62→84px）
  → 発射（4.1s、`blast`＋`shake hard`＋衝撃波）→ 画面外へ（5.2sで炎の下端Y=-595）
  → 6.5sでリセットの流れを実測
- 発射中に「さいしょから」を押しても、残りのタイマーが動かず盤面が戻ることを確認
- モバイル（375×812）で口数2/6/9/12すべて、ボタン・ロケット・弁当箱・トップバーの
  重なりと画面外はみ出しなし。設定パネルも画面内に収まる
- 口数・検知・リングサイズがリロード後に復元されることを確認
- 実行時エラーなし

未検証: 実機カメラでの検知精度、および実際のアニメーション表示
（検証環境ではブラウザペインが非表示のため、`requestAnimationFrame` と

## 2026-08-18 発射後の処理落ちの原因調査と修正、エフェクト実装ルールの明文化

対象ファイル: `index.html`、`CLAUDE.md`（新規）

### 症状

ロケット発射後に処理が重くなる。

### 原因（計測で特定）

推測せず、実際の粒の構成を再現してベンチマークを取った。

| 条件（375×812・デスクトップ実測） | 1フレーム |
|---|---|
| 修正前・発射直後 1244個 | 38.45ms（26fps） |
| スプライト化のみ | 9.86ms |
| 個数削減のみ 340個 | 13.39ms |
| 両方 | 3.19ms |

種類ごとに切り分けると **絵文字400個で28.0ms**、**火花800個で17.6ms**。
原因は「1粒ごとに毎フレーム、重いCanvas APIを呼んでいた」ことで、具体的には
`ctx.font` への代入と `fillText`（フォント解決＋絵文字カラーグリフのラスタライズ）、
および `createRadialGradient` の毎粒毎フレーム生成。
デスクトップでこの数字なので、実機のスマホは3〜5倍かかる。

粒の量そのものも過剰だった。発射時の内訳は
噴射 35ms間隔×16個×1.9秒 ≒ 864個、煙44個、星のバースト 12回×34個 = 408個で、
上限1200個に張り付いていた。

### 修正

**描画方式（効果が大きい方）**

- 絵柄を起動時に一度だけ 64×64 のキャンバスへ焼く（スプライト化）。
  火花は色相6種、煙1種、絵文字は使うぶんだけ。毎フレームは `drawImage` のみ
- 種類ごとにまとめて描き、`globalCompositeOperation` の切替を1フレーム2回に抑制
- 1粒ごとの `save()` / `restore()` を廃止し、`globalAlpha` と `setTransform` を直接操作
- 上限を1200→460個に。超過分は `slice`（新配列を作る）ではなく `splice` で古い順に破棄

**生成数**

| 場面 | 修正前 | 修正後 |
|---|---|---|
| ひとくちのバースト | 46 | 28 |
| ひとくちの噴射 | 10 | 7 |
| カウントダウンの噴射 | 10+i×6 | 8+i×4 |
| 発射の煙 | 44 | 22 |
| 発射の噴射 | 35ms間隔×16 | 55ms間隔×9 |
| 星のバースト | 12回×34 | 7回×22 |

**自動減量**

描画ループでフレーム時間を指数移動平均で監視し、26msを超えたら `fxScale` を
0.35まで段階的に下げ、19msを下回ったらゆっくり戻す。粒の生成数はすべて
`amount(n)` を通す。タブ復帰などの100ms超の飛びは計測に混ぜない。

### 効果（発射シーケンスを通しで実測）

| 指標 | 結果 |
|---|---|
| 粒のピーク | 290個（修正前は上限1200に張り付き） |
| 平均 | 0.28ms |
| 中央値 | 0.10ms |
| p95 | 1.40ms |
| 最大 | 4.10ms |
| 16.7ms超過フレーム | 877フレーム中 **0** |

描画結果も確認（絵文字バースト6196px・火花3259px、粒は寿命どおり0まで減る）。
実行時エラーなし。

### 再発防止

`CLAUDE.md` を新規作成し、原因・数値・ルール・計測手順を明文化した。

1. 毎フレームのループ内で `createRadialGradient` / `ctx.font` 代入 / `fillText` /
   `getBoundingClientRect` / オブジェクト生成をしない。起動時スプライト＋`drawImage`
2. 同時に生きる粒に必ず上限。破棄は `splice`
3. 種類ごとにまとめ描き。合成モード切替は1フレーム2回まで。粒ごとの `save/restore` 禁止
4. フレーム時間を監視して重い端末では自動減量
5. `setInterval` のエミッタは停止タイマーとリセット処理の両方から止める
6. CSS アニメーションは `transform` と `opacity` のみ
7. `prefers-reduced-motion` の分岐を必ず用意
8. 受け入れ基準: デスクトップ実測で p95 8ms 未満／最大 16.7ms 未満／予算超過0。
   見た目で判断せず必ず数字を出す（計測用スニペットを CLAUDE.md に収録）

診断用に `window.__mogu` へ `parts` / `fxScale` / `frameMs` を追加した。

示していて役割が重複していた。同じことを2か所で見せると視線が散るため、

- `showRocket()` を `showBoards()` に置き換え、設定「ロケット」で
  燃料ゲージとおべんとう箱を排他に切り替えるようにした

| ロケット | 出るもの | 完成時の言葉 |
|---|---|---|

  セグメントの角丸と最小高さも上げた

## 2026-08-19 責任の分割（ES モジュール化）と、演出プラグイン化・新テーマ2種

### 経緯

`index.html` 1ファイルに HTML / CSS / JS がすべて入っており、1034行になっていた。
演出を増やすたびに同じファイルが膨らみ、検知の修正と演出の修正が同じ場所で

という要望が出た時点で、増やす前に構造を変えることにした。

### 分割の方針

**「ひとくち検知して数える」核と、「それをどう見せるか」を完全に切り離す。**
核は演出を1つも知らず、演出は検知を1つも知らない。

```
index.html          骨組みだけ
styles/base.css     共通の見た目
styles/themes.css   テーマごとの見た目
src/main.js         組み立て役。線をつなぐだけで何も判断しない
src/config.js       差し替えたいものを1か所に
src/core/           bus（連絡） / store（設定） / state（進行状態）
src/input/          camera / motion（検知） / ring（わっか操作）
src/fx/             particles / sound / screen
src/ui/             panel / hud
src/themes/         index + bento / rocket / princess / patrol
```

モジュール同士は直接呼ばず、必ずイベントバスを通す。
受け手を足すときに送り手を触らなくて済むようにするため。

### テーマ（演出プラグイン）

演出を増やすことが最も頻繁な変更だと想定し、
**テーマを足すときに既存コードを一切触らなくてよい**形にした。

実装するのは `mount / unmount / build / progress / bite / celebrate / reset` の7つ。
`src/themes/index.js` の配列に足せば、設定パネルの選択肢にも自動で出る。

テーマには ctx で道具を渡す（`fx` / `sound` / `speech` / `shout` / `screen` /
`later` / `every` / `figure` / `setDeck`）。

`later` / `every` をコア側で管理しているのは、CLAUDE.md のルール
「`setInterval` のエミッタは必ず止める」を、テーマ作者が意識しなくても
守られる形にするため。リセットと切り替えで一括して止まる。

### 新しいテーマ

**おひめさま** — ひとくちごとに身につけるものが円周上に増えていく。
完了すると中央へ進み出て、👧 から 👸 に入れ替わり、ドレスが咲いて
花びらが降りそそぐ。

**パトロール** — ひとくちごとにランプが灯る。完了するとランプが赤青に
切り替わってサイレンが鳴り、主役が中央に出てから画面を横切って出発する。

主役の絵は `config.js` の `assets` にパスを書くと画像に、
未設定なら絵文字にフォールバックする。テーマは `ctx.figure()` を使うかぎり
画像の有無を気にしなくてよい。`assets/` は `.gitignore` した。

### 計測でつまずいた点（CLAUDE.md に追記）

ブラウザの HTTP キャッシュで、編集したモジュールが古いまま配信され続け、
「直したのに直らない」状態になった。ディスク上のファイルと、
`fetch` で取得した内容と、実際に `import` されたモジュールの3つを
突き合わせて初めて気づいた。別ポートで開き直して解決。

同様に `read_console_messages` はタブ全体のエラー履歴を累積するため、
修正前のエラーが残り続ける。修正後は新規カウンタを置いて判定すること。
